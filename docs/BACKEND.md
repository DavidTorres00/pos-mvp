## Seguridad
- Auth: cookie httpOnly (`access_token`, JWT) + cookie legible (`csrf_token`). Login vía `auth_service.iniciar_sesion`, cookies las setea el router.
- CSRF: patrón double-submit (`app/core/csrf.py`, `CSRFMiddleware`). Todo método mutante exige header `X-CSRF-Token` == cookie `csrf_token`, o 403.
- RBAC: `Usuario.role` (`admin` | `cajero`), dependency `require_role` (`app/api/deps.py`). Admin-only: `categorias`/`subcategorias` completo (lectura **y** mutación — el cajero no ve el árbol de catálogo, solo el producto ya categorizado), mutaciones de productos, `compras` completo, `proveedores` completo, `configuracion` completo, `auditoria` completo, `usuarios` (gestión, incluye alta) completo, `reportes` completo, `inventario/movimientos` completo (lectura y escritura), `sucursales`/`equipos` completo. Cajero: ventas, productos (lectura), caja completo (incluye `retirar-excedente` si tiene el permiso, ver más abajo, y `POST /caja/abrir` — forzado a rol cajero, ver Multisucursal).
- Permiso fino por usuario: `Usuario.puede_retirar_excedente` y `Usuario.puede_hacer_devoluciones` (booleanos independientes, `PATCH /usuarios/{id}/permisos` acepta ambos, cada uno opcional — la UI cambia uno a la vez) habilitan a un cajero puntual a ejecutar `POST /caja/retirar-excedente` / `POST /ventas/{id}/devoluciones` respectivamente; un admin siempre puede ambos sin importar el flag.
- Transacción por request: `get_db` commitea solo si el request completa sin excepción, rollback automático si falla algo — ninguna operación multi-paso (venta, compra, aprobación de pago a proveedor) puede quedar a medias. Los repositorios solo hacen `flush()`, nunca commit individual.
  - Excepción deliberada: `auditoria_service.registrar_evento_independiente` abre su propia sesión y hace commit inmediato, para eventos que deben sobrevivir aunque la request termine en excepción (ej. login fallido, que siempre responde 401 y revertiría la transacción ambiente junto con el registro que se quiere conservar).
- Concurrencia: `stock_sucursal_repository.get_or_create_for_update` (`SELECT FOR UPDATE` sobre la fila producto×sucursal, crea la fila perezosamente con lock si no existía) al mutar stock; `caja_repository.get_abierta_for_update_by_usuario` al retirar excedente; `compra_repository.get_by_id_for_update` al aprobar/rechazar/recibir un pedido — evita que un doble clic (o el admin y otra pestaña a la vez) dupliquen el pago o la recepción. Índices únicos parciales (no modelados en SQLAlchemy, cuidado con `alembic revision --autogenerate`: los marca como "removidos" por error, no tocar):
  - `caja_sesiones (equipo_id) WHERE abierta=true` y `caja_sesiones (usuario_id) WHERE abierta=true` — N cajas pueden estar abiertas a la vez, una por equipo y una por cajero (ver Multisucursal).
  - `CHECK (stock >= 0)` en `stock_sucursal` (`ck_stock_sucursal_no_negativo`) — `productos.stock` no existe (ver Fase 2).
  - Unicidad de nombre/SKU/CLABE-por-proveedor verificada con SAVEPOINT + traducción de `IntegrityError` al error de dominio (no solo pre-check en Python).
- Errores: handler global `IntegrityError`→409, `Exception`→500 JSON con logging (`app/main.py`) — nunca se expone un traceback crudo.

## Paginación
Los endpoints de listado (`productos`, `categorias`, `subcategorias`, `compras`, `ventas`, `proveedores`, `usuarios`, `auditoria`, `inventario/movimientos`, `caja/movimientos`, `sucursales`, `equipos`) devuelven `Pagina[T]` (`app/schemas/pagination.py`): `{items, total, page, size}`. ## Estado
Roadmap completo implementado, incluida la fase de "sistema real de negocio" (auditoría, límite de caja, proveedores, pago a proveedor vía pedido manual, forma de pago en ventas). **Sin reorden automático**: decisión de negocio explícita, un pedido a proveedor y su pago siempre son un acto manual del admin — el sistema nunca dispara uno solo por cruzar un umbral de stock (ver Compras más abajo).

- `GET /api/health` (`app/api/router.py`): sondeo de conectividad sin auth ni DB — `{"status": "ok"}` fijo. Es el endpoint que consume el heartbeat del frontend (`useSaludServidor`, ver `docs/FRONTEND.md`) para detectar si el backend responde, sin pagar el costo de un lookup a base de datos en cada tick.
- Login: `usuarios` (modelo, repository, service, router `/api/auth/login` + `/api/auth/me`), JWT sin refresh token, seed de admin vía `scripts/seed_admin.py` (rol admin explícito). Login éxito/fallido queda registrado en `auditoria` (fallido con sesión independiente, ver Seguridad).
- `scripts/seed_demo.py` (`PYTHONPATH=. .venv/bin/python scripts/seed_demo.py`, destructivo): repuebla la base para probar contra un entorno "de producción" — 3 sucursales × 3 equipos, catálogo sintético (conserva `Categoria`/`Subcategoria` reales, regenera `Producto`/`Proveedor`) y ~30 días de historial ejecutando los `service` reales (venta/caja/compra), no INSERTs crudos, para que auditoría/snapshots de stock/límites de caja queden exactamente como si el mes hubiera pasado de verdad. Cada compra generada lleva `costo_unitario = precio_venta × 0.55` — al pasar por `compra_service.recibir` real, sincroniza `Producto.costo` desde el primer pedido (el que arma el stock inicial), así toda venta simulada del mes congela un `costo_unitario` real y `GET /ventas/resumen` reporta ~45% de margen con cobertura completa, sin ningún caso especial en el script para esto. Los timestamps se reescriben después de cada acción (`retag`, vía `UPDATE ... WHERE id > antes_de`) porque los services solo saben "ahora" — ver el propio script para el detalle.
- Gestión de usuarios: `GET /api/usuarios` (admin, paginado, solo lista `role=cajero` — el admin no se lista a sí mismo), `POST /api/usuarios` (admin, alta de cajero con password directo, sin flujo de invitación/reset), `PATCH /api/usuarios/{id}/permisos` (admin, otorga/quita `puede_retirar_excedente`/`puede_hacer_devoluciones`). Alta de un segundo admin sigue sin endpoint — se crea por `seed_admin.py`/acceso directo a DB.
  - Edición del cajero: `PATCH /api/usuarios/{id}` (`UsuarioUpdate`, todos los campos opcionales — `nombre`/`email`/`sucursal_id`/`activo`, cualquier combinación en una sola request, un solo evento `usuario_actualizado` en auditoría con el diff real de lo que cambió) — un único endpoint consolidado para toda edición de datos del cajero, sin uno separado por campo. `activo`/`sucursal_id` son sensibles al negocio, no simples setters:
    - Cambiar de sucursal o pasar `activo=false` con el cajero **con una caja abierta ahora mismo** (`caja_repository.get_abierta_by_usuario`) se rechaza con `CajaAbiertaError` (400) — desactivarlo o reubicarlo a medio turno dejaría dinero/inventario sin dueño claro. El admin debe cerrar esa caja primero (corte de emergencia si el cajero no puede, ver `caja_service.cerrar` arriba). Reactivar (`activo=true`) o dejar la sucursal sin cambios nunca dispara este chequeo.
    - `email` valida duplicado igual que el alta (`EmailDuplicadoError`, 409).
    - Deliberadamente **no** incluye `puede_retirar_excedente`/`puede_hacer_devoluciones` (siguen en `/permisos`, son los switches de la tabla, otro flujo) ni la contraseña (endpoint aparte, ver abajo — un campo de password nunca debe viajar silencioso dentro de una edición general de varios campos).
  - Reseteo de contraseña: `POST /api/usuarios/{id}/resetear-password` (`UsuarioPasswordUpdate`, mismas reglas de longitud que el alta) — el admin pone una contraseña nueva directo, sin flujo de email/token (no existe ese sistema, mismo criterio que el alta de cajero). Auditado como `usuario_password_reseteada` sin el valor de la contraseña en el detalle — el evento en sí ya es la señal que importa. No exige caja cerrada: cambiar la contraseña no afecta una sesión JWT ya emitida (sin revocación por jti, ver Seguridad arriba), así que no interrumpe un turno en curso.
- Auditoría (`app/models/auditoria.py`): tabla transversal `{usuario_id (nullable), accion, entidad, entidad_id, detalle JSON, created_at}`. Poblada desde los `service` en cada mutación relevante (login, producto: creación/cambio de precio/cambio de estado, apertura/cierre de caja, movimientos de caja, retiro de excedente, ventas, proveedores, cada transición de un pedido a proveedor). No reemplaza `usuario_id`/`created_at` de cada tabla de dominio — es el punto único de consulta "quién hizo qué" sin recorrer módulo por módulo. Endpoint `GET /api/auditoria` admin-only, filtros `usuario_id`/`entidad`/`desde`/`hasta`.
- Sesión de cajero: **sigue sin existir tabla `sesiones_usuario`** (JWT stateless, sin revocación por jti — decisión deliberada, no se necesitaba forzar cierre de sesión de otro usuario). Reglas para que un cajero siempre sepa si hay una caja abierta y de quién es antes de tomarla:
  - `POST /auth/logout` pasa por `auth_service.cerrar_sesion`: si el usuario tiene su propia caja abierta (`caja_repository.get_abierta_by_usuario`), rechaza el logout con 409 (`CajaAbiertaPropiaError`) — debe hacer el corte primero, para que el siguiente cajero empiece limpio con su propio `monto_inicial`. Si no, registra `logout` en auditoría.
  - Caso de emergencia (cajero no puede hacer su propio corte): `caja_service.cerrar(db, actor_id, target_usuario_id, monto_final, motivo_diferencia=None)` no exige que `actor_id == target_usuario_id` — el admin cierra la caja de cualquier cajero vía `POST /usuarios/{id}/caja/cerrar` (ver Multisucursal), auditado con el `actor_id` real. El admin no puede forzar el logout de otro usuario — hay dinero de por medio (caja abierta), y esa acción no existe por diseño.
  - Control de diferencia al cierre: `cerrar()` calcula `monto_esperado` **antes** de tocar la caja (así puede rechazar el cierre sin dejarlo a medias) y compara contra `monto_final`. Si el resultado es **faltante** (`diferencia < 0`) y no viene `motivo_diferencia` (no vacío), 400 (`MotivoDiferenciaRequeridoError`) — no se puede cerrar sin explicar de dónde salió el faltante. Un **sobrante** (`diferencia > 0`) no exige nada: no es una pérdida, así que no se bloquea el cierre (`motivo_diferencia` sigue siendo válido si el cajero quiere dejar una nota, pero es opcional). `motivo_diferencia` viaja en `CajaCerrarRequest` y queda en el `detalle` del evento `caja_cerrada` de `auditoria` junto con `monto_final`/`diferencia` — sigue sin existir una vista dedicada de "cortes de caja" para el admin más allá de este log (ver `docs/FRONTEND.md`, pendiente si se necesita).
- Configuración de negocio (`app/models/configuracion_negocio.py`): fila única (id=1, creada por migración) con `limite_efectivo_caja`, `umbral_stock_bajo_default`, editable en runtime sin redeploy vía `GET`/`PUT /api/configuracion` (admin-only). Distinto de `Settings`/`.env` (eso es config de despliegue: secretos, infra). `limite_efectivo_caja` aquí es el **default global** — cada `Sucursal` puede tener su propio override (ver Multisucursal), que gana cuando está configurado. **Sin ningún tope de gasto para pagar a proveedor** — decisión deliberada: la revisión manual del admin en cada pedido ya es el control, un segundo tope automático sería redundante.
  - `umbral_stock_bajo_default` (`int | None`): nulo = feature apagada. Alimenta la alerta `stock_bajo` del reporte de atención (ver más abajo) — cantidad en o debajo de la cual cualquier producto se considera "bajo".
- Caja: `caja_sesiones` (N abiertas a la vez desde Multisucursal Fase 1 — una por equipo, una por cajero, ver más abajo) + `movimientos_caja` (con `usuario_id` obligatorio — todo movimiento queda atado a quién lo hizo, sin excepción). `caja_service`: abrir/cerrar/resumen (monto esperado = inicial + ventas **en efectivo** + entradas − salidas; ventas con tarjeta/transferencia no suman al efectivo físico). `GET /api/caja/actual` (scopeada a "mi caja", ver Multisucursal) devuelve además `efectivo_actual`, `limite_efectivo` y `excede_limite`.
  - `caja_service.limite_efectivo_para_sucursal(db, sucursal_id)`: único punto donde se resuelve el límite de efectivo vigente — el override de `Sucursal.limite_efectivo_caja` si está configurado, si no `configuracion_negocio.limite_efectivo_caja`. Todo lo que compara efectivo contra un límite (`abrir`, `excede_limite`, `obtener_actual`, `retirar_excedente`, `reporte_service.resumen_sucursales`, la alerta `caja_excedida`) pasa por aquí — nunca lee `configuracion_negocio` directo cuando ya hay una sucursal de por medio. `CajaResumenOut.limite_efectivo` lleva este valor ya resuelto en cada fila de `GET /reportes/cajas-abiertas`/`resumen()` — cualquier pantalla que liste cajas de varias sucursales a la vez compara cada una contra su propio límite, no contra uno global compartido.
  - No existe `POST /api/caja/movimientos` (creación manual de entrada/salida libre) — no queda ningún caso real que lo justifique (cambio de billete/moneda no altera el total de la caja, así que no es un movimiento; retiro del dueño no aplica, para pagos a terceros ya existe el módulo de Proveedores). Todo movimiento que no sea una venta debe salir de una acción real y automática (hoy: retiro de excedente; a futuro: Recargas/Retiros/Transferencias/Pagos de servicios del kiosko), nunca de que el cajero lo declare a mano. `GET /api/caja/movimientos` (listado) existe sin consumidor en el frontend por ahora — es la base para la futura vista de historial del admin.
  - `abrir` valida `monto_inicial` contra `limite_efectivo_caja` **antes** de crear la caja: si lo supera, 400 (`MontoInicialExcedeLimiteError`) y no se crea nada.
  - `CajaActualOut.ultimo_cierre`: cuando el cajero no tiene caja abierta, expone `fecha_cierre` de la última que ÉL cerró (`caja_repository.get_ultima_cerrada_by_usuario`) — lo consume el splash de apertura del cajero en el frontend. Es "la última vez que este cajero cerró", no la del equipo: un cajero puede rotar de equipo entre turnos.
  - `CajaOut.usuario_nombre`/`equipo_nombre` (relationships `CajaSesion.usuario`/`.equipo`, `lazy="joined"`): identifica quién abrió la caja y en qué equipo. `CajaOut.sucursal_nombre`/`sucursal_direccion` (properties `CajaSesion.sucursal_nombre`/`sucursal_direccion` → `self.equipo.sucursal.nombre`/`.direccion`, reusan el mismo `lazy="joined"` de `Equipo.sucursal`) permiten al kiosko del cajero (frontend) mostrar sucursal y dirección sin otra consulta — `sucursal_direccion` viaja igual en `VoucherRetiroOut` (`_voucher_desde_movimiento`), para el encabezado de los comprobantes impresos (ver `docs/FRONTEND.md`).
  - `caja_service.excede_limite(db, caja)` (público, usado por `venta_service`): true si el efectivo esperado de la caja YA supera el límite, antes de considerar ninguna venta nueva. `venta_service.crear` lo chequea y bloquea con `LimiteEfectivoExcedidoError` (409) **cualquier** venta nueva (sea cual sea `forma_pago`) mientras la caja siga excedida — la venta que provoca el exceso se permite (no queda a medias), pero ninguna otra hasta que se retire el excedente. Regla de negocio explícita: no depende de que el cajero se acuerde de retirar el excedente por su cuenta.
  - `cerrar(db, actor_id, target_usuario_id, monto_final, motivo_diferencia)` no exige `actor_id == target_usuario_id` — cubre tanto el cajero cerrando la suya como el admin cerrando la de otro (corte de emergencia), auditado siempre con el `actor_id` real.
  - Retiro de excedente: `caja_service.retirar_excedente(db, actor, target_usuario_id)` — mismo patrón actor/target que `cerrar()`. Si el efectivo de la caja de `target_usuario_id` supera el límite configurado, retira exactamente el excedente (deja la caja en el `monto_inicial`), genera el `MovimientoCaja` de salida (auditado con `actor.id`, no con el dueño de la caja; `motivo` fijo `caja_repository.MOTIVO_RETIRO_EXCEDENTE`, así se puede distinguir de una salida manual cualquiera sin agregar columna) y un voucher (`VoucherRetiroOut`, `cajero`/`sucursal_nombre`/`equipo_nombre` = los de la caja del dueño, no del actor; `autorizado_por` = `movimiento.usuario_nombre`, quién ejecutó — relationship `MovimientoCaja.usuario`/`usuario_nombre`, mismo patrón que `CajaSesion`) con los datos para imprimir — construcción del voucher centralizada en `_voucher_desde_movimiento(movimiento, caja)`, que también usa lo siguiente. Un cajero solo puede retirar la suya (`puede_retirar_excedente` y `target == actor`); el admin puede la de cualquiera — cuadre de caja rutinario, no un caso de emergencia, así que no está gateado a "solo si el cajero no puede". Dos endpoints: `POST /api/caja/retirar-excedente` (self-service, `target = usuario.id`) y `POST /api/usuarios/{id}/caja/retirar-excedente` (admin-only, mismo servicio con `target = {id}`, análogo a `/usuarios/{id}/caja/cerrar`). Usa lock de fila para que dos intentos concurrentes (p. ej. el propio cajero y el admin a la vez) no dupliquen el retiro.
  - Problema físico real: el comprobante tiene que imprimirse en el dispositivo que está junto al efectivo (la caja del cajero), no en el del actor que dispara la acción — la impresión (vía QZ Tray, ver `docs/FRONTEND.md`) siempre ocurre en la máquina que la ejecuta. Si el admin retira remoto (no está físicamente en la sucursal), su equipo no puede imprimir en la caja del cajero. Por eso el admin (hub de Sucursales) no muestra ningún comprobante — a él solo le interesa liberar la caja, ver `docs/FRONTEND.md`. `caja_service.obtener_ultimo_retiro_excedente(db, usuario_id)` (`GET /api/caja/ultimo-retiro-excedente`) devuelve el voucher del último retiro de excedente de la caja abierta del que llama, reconstruido igual que el original (`efectivo_anterior` se deriva de `monto_inicial + movimiento.monto`, matemáticamente idéntico al valor en el momento del retiro porque el retiro siempre deja la caja en `monto_inicial`). El frontend del cajero lo consulta cuando detecta (por SSE o por polling, ver más abajo) que su propia caja dejó de estar excedida sin que él mismo la haya retirado.
  - Notificación en tiempo real (`app/core/eventos_caja.py`, `RegistroEventosCaja`): pub/sub en memoria del proceso, scopeado por `usuario_id` — no por rol. Un cajero solo tiene una caja abierta a la vez en un equipo, así que `usuario_id` ya identifica sin ambigüedad esa sesión de caja/equipo puntual; nunca se notifica a "todos los cajeros" ni se transmite por rol. `caja_service.retirar_excedente`/`cerrar` llaman `eventos_caja.notificar(target_usuario_id)` justo antes de retornar — cubre tanto el self-service como el corte/retiro remoto del admin, porque ambos casos pasan por la misma función de servicio. `GET /api/caja/eventos` (Server-Sent Events, `app/modules/caja/router.py`) suscribe al `usuario_id` autenticado y hace streaming de un evento `cambio` cada vez que le llega una notificación, con keep-alive cada 25s mientras no pasa nada. El payload no importa — es solo una señal de "vuelve a pedir tu caja actual"; la única fuente de verdad sigue siendo `GET /caja/actual`. Complementa al polling de 15s del frontend (`useCajaActual`), no lo reemplaza: si el navegador no soporta streams o la conexión SSE se cae, el polling sigue cubriendo sin que nada se rompa — ninguno de los dos canales es el único punto de falla, y como ninguno transporta el estado en sí (solo disparan el mismo refetch), nunca pueden desincronizarse entre sí. En memoria porque el backend corre en una sola instancia; escalar a varios procesos necesitaría pub/sub real (Redis) en vez del dict actual.
  - `/eventos` vive en `eventos_router`, un `APIRouter` aparte del resto de `/caja` (mismo prefix, montado por separado) — deliberadamente sin el `dependencies=[Depends(get_current_user)]` a nivel de router que sí llevan los demás endpoints de caja. Una dependencia `yield` como `get_db` solo corre su `finally` (commit/close) cuando la *respuesta completa* termina de enviarse; para un `StreamingResponse` eso es cuando el stream se cierra, lo cual no ocurre si el cliente se desconecta sin avisar (laptop cerrada, cambio de red, wifi que cae sin mandar FIN/RST) — la sesión de Postgres quedaría "idle in transaction" indefinidamente. `resolver_usuario_desde_cookie(db, request)` (`app/api/deps.py`) resuelve el usuario desde la cookie con cualquier sesión de DB que se le pase — es la misma lógica que usa `get_current_user`, sin atarla a la sesión de un request normal. `/eventos` lo llama con un `SessionLocal()` de vida corta (`with SessionLocal() as db: ...`), cerrada *antes* de empezar a transmitir; el resto del stream vive puramente en memoria (la cola de `eventos_caja`), sin ninguna conexión a la base de datos abierta.
- Productos: `productos` (soft delete vía `activo`, router `/api/productos`). Cambios de precio y de estado quedan auditados con el valor anterior/nuevo. `GET /productos` acepta filtros opcionales `activo: bool`, `categoria_id: int`, `proveedor_id: int` (`producto_repository.get_all`) — el admin omite `activo` (ve todo, para poder reactivar), el picker de productos del cajero (frontend) lo manda siempre en `true`; `categoria_id` alimenta el panel de detalle del hub de Productos, `proveedor_id` alimenta la tabla de "sus productos" dentro del hub de Proveedores (ver `docs/FRONTEND.md`, ambos hubs).
  - `Producto.costo` (nullable): base de la utilidad/margen del hub de Ventas. `compra_service.recibir` lo sincroniza solo con el `costo_unitario` de cada línea recibida (lo último que de verdad se pagó); editable a mano en `ProductoForm` para cargar el costo inicial antes de la primera compra registrada. Nunca se infiere en 0 — un producto sin costo cargado queda fuera del cálculo de utilidad, no lo infla artificialmente.
  - `DetalleVenta.costo_unitario` (nullable): congelado desde `Producto.costo` en `venta_service.crear`, mismo criterio que `precio_unitario` — la utilidad de una venta no cambia después si el costo del producto cambia más tarde. `DetalleVenta.utilidad` (property) = `(precio_unitario − costo_unitario) × cantidad`, `None` si `costo_unitario` es `None`.
  - `producto_repository.get_all` trae el stock de la sucursal (`StockSucursal.cantidad`) en la misma consulta (`outerjoin`, no una segunda vuelta a la base) para ordenar en tres niveles, el más urgente primero: sin stock (cantidad en 0 o sin fila para esa sucursal), stock bajo (cantidad ≤ `umbral_stock_bajo_default`, si hay uno configurado), normal — alfabético dentro de cada nivel. Mismo criterio que las alertas del dashboard (`reporte_service`). El resultado ya trae la cantidad junto con cada `Producto`, así que `producto_service.listar` no necesita una consulta aparte a `stock_sucursal_repository.get_cantidades` para armar el stock de cada fila (sí la sigue usando `obtener()`/`venta_service`, que resuelven un producto puntual, no un listado paginado).
  - `Producto.proveedor_id` (opcional, FK a `Proveedor`): quién surte habitualmente ese producto, a nivel catálogo — **informativo/default, no restrictivo**: `compra_service.crear` no exige que coincida con nada, un admin puede armarle un pedido de cualquier producto a cualquier proveedor si la realidad cambia. No es por sucursal: el catálogo es global.
- Categorías y Subcategorías (§ catalogación real, `app/models/categoria.py` + `app/models/subcategoria.py`): jerarquía de 2 niveles con **código numérico auto-secuencial** (`Categoria.codigo`, `Subcategoria.codigo`, ambos `String(2)`, únicos dentro de su padre — asignados por `_siguiente_codigo` en cada `service.crear`, nunca elegidos por el usuario). Techo duro de 99 subcategorías por categoría (el código no cabe en `String(2)` más allá de "99"), deliberado — evita necesitar paginación en el listado por categoría. `GET /categorias` y `GET /subcategorias` son **admin-only** — el cajero solo ve el catálogo aplanado vía `Producto.categoria`/`Producto.subcategoria`. Catálogo semilla de 12 categorías / 62 subcategorías (migración `f39b82803b11`), con `docs/info-categorias-productos.pdf` como referencia.
  - `CategoriaResumenOut` (`CategoriaOut` + `total_subcategorias`/`total_productos`, subcategorías totales y productos **activos**, + `productos_sin_stock`/`productos_stock_bajo`): es lo que devuelven todos los endpoints de `/categorias` — `CategoriaOut` en sí queda puro (id/nombre/codigo/activo), porque también viaja embebido en `ProductoOut.categoria`/`SubcategoriaOut.categoria` (ventas, compras, movimientos), que nunca calculan esos conteos; mismo split que `ProductoOut`/`ProductoStockOut`. Los conteos no son columnas del ORM: se resuelven en `categoria_service` vía `categoria_repository.get_conteos(db, categoria_ids)` (dos `GROUP BY`, sin N+1 por categoría) y se construyen a mano en cada función del service. Alimentan el maestro del hub de Productos en el frontend (ver `docs/FRONTEND.md`) — "N subcategorías · M productos" por categoría, sin necesitar un endpoint de resumen aparte.
  - `GET /categorias` acepta `sucursal_id: int` opcional — si viene, `productos_sin_stock`/`productos_stock_bajo` cuentan los productos activos de esa categoría en cada estado, en esa sucursal (`categoria_repository.get_conteos_alerta_stock`, mismo criterio de tres niveles que `producto_repository.get_all`/`reporte_service`: `outerjoin` con `StockSucursal`, sin fila o `cantidad` en 0 = sin stock; `cantidad` ≤ `umbral_stock_bajo_default` = stock bajo, mutuamente excluyentes). Sin `sucursal_id` (el picker de categoría en `ProductoForm`, que no necesita saber de stock), ambos son siempre `0` — no es un "sin alertas" real, es solo que nadie preguntó.
- Productos: `Producto.subcategoria_id` (opcional, FK) coexiste con `categoria_id` directo. Si se crea un producto con `subcategoria_id`, el SKU se **autogenera** (`codigo_categoria + codigo_subcategoria + secuencial de 2 dígitos`, ej. `010101`) y `categoria_id` se deriva del padre de la subcategoría — el campo `sku` del payload se ignora en ese caso. Sin `subcategoria_id`, el flujo es: SKU manual obligatorio + `categoria_id` opcional directo. Al editar, el SKU nunca se regenera automáticamente (evita romper códigos de barra ya impresos).
- Inventario: stock por sucursal (`stock_sucursal`, ver Multisucursal Fase 2 — `Producto` no tiene columna de stock propia). `movimientos_inventario` vía `inventario_service.registrar_movimiento` con lock de fila (sobre `stock_sucursal`, no sobre `Producto`), con **auditoría propia** (cada movimiento queda registrado en `auditoria`) y `stock_resultante` (snapshot del stock de esa sucursal justo después de ese movimiento, columna propia — no se lee del stock actual, que cambia con movimientos posteriores). `GET /inventario/movimientos` es admin-only, scopeado a una sucursal (`resolve_sucursal_id`, ver Multisucursal) y acepta filtros `q` (nombre/SKU), `tipo`, `desde`/`hasta`. **No dispara nada automático tras una salida** — cualquier reabasto es un pedido que el admin arma a mano (ver Compras).
- Compras — pedido a proveedor con ciclo de vida propio, siempre armado y aprobado por el admin, nunca disparado por el sistema: el pago es dinero real, y la revisión manual del admin es el único control (sin automatización posible):
  - `Compra` (cabecera: `proveedor_id`, `sucursal_id`, `total`, `usuario_id` — quién armó el pedido) + `DetalleCompra` (líneas: `producto_id`, `cantidad` pedida, `costo_unitario`, `subtotal`, `cantidad_recibida` nullable). `Compra.sucursal_id` (FK, requerido desde Fase 2) — un pedido completo llega a una sola sucursal, resuelta vía `resolve_sucursal_id`. `GET /compras` acepta `proveedor_id` opcional, además de la sucursal — alimenta tanto el historial general como la tabla de pedidos de un proveedor puntual en su hub (ver `docs/FRONTEND.md`).
  - `EstadoCompra` (`app/models/compra.py`): `pendiente → pagada`/`error` (vía `POST /compras/{id}/aprobar`) `→ recibida` (vía `POST /compras/{id}/recibir`); o `pendiente → rechazada` (`POST /compras/{id}/rechazar`, solo cancela antes de pagar — una vez pagado no hay marcha atrás). Tres momentos deliberadamente separados, nunca colapsados en uno:
    1. **Armar** (`compra_service.crear`, `POST /compras`): valida proveedor/productos, calcula `total`, queda `pendiente`. **No toca Inventario ni dispara ningún pago** — armar el pedido es solo la propuesta.
    2. **Aprobar y pagar** (`compra_service.aprobar_y_pagar`, admin): dispara el pago real vía OpenPay a la CLABE del proveedor (`ProveedorSinDatosPagoError` si no la tiene cargada). **Sin ningún tope de gasto que lo bloquee** (ver Configuración arriba) — la revisión manual de este mismo clic ya es el control. Si OpenPay falla, la compra queda en `error` (con el mensaje, sin relanzar excepción — mismo motivo que el login fallido en `auth_service`: lanzarla revertiría el registro de la falla junto con la transacción). Lock de fila (`compra_repository.get_by_id_for_update`) evita que un doble clic pague dos veces.
    3. **Recibir** (`compra_service.recibir`, admin, solo desde `pagada`): la mercancía llegó físicamente a la sucursal — recién aquí se generan los movimientos de entrada en Inventario, uno por línea, con `cantidad_recibida` (no `cantidad` pedida) — puede ser menos si el proveedor entregó incompleto. El payload debe cubrir **exactamente** los productos del pedido, uno por uno (`DetalleIncompletoError` si falta alguno) — sin default implícito, para no adivinar qué llegó y qué no.
- Proveedores (`app/models/proveedor.py`): entidad real — `nombre` (único), `contacto`, `telefono`, `email`, `clabe` (CLABE interbancaria, destino del pago cuando el admin aprueba un pedido — nunca automático). CRUD admin-only en `/api/proveedores`, mismo patrón que `categorias`. Catálogo global, no por sucursal.
  - `ProveedorResumenOut` (`ProveedorOut` + `total_productos`/`pedidos_pendientes`, mismo patrón que `CategoriaResumenOut`): lo que devuelven todos los endpoints de `/proveedores` — `ProveedorOut` en sí queda puro porque también viaja embebido en `ProductoOut.proveedor`/`CompraOut.proveedor`, que nunca calculan esos conteos. `proveedor_repository.get_conteos` (dos `GROUP BY`, sin N+1). Alimenta el maestro del hub de Proveedores en el frontend (ver `docs/FRONTEND.md`).
- Pago a proveedor vía OpenPay (`app/core/openpay_client.py`): sin el SDK oficial `openpay` (PyPI) — ese paquete usa `use_2to3` y no compila en Python 3.13. Llama directo a la API REST de OpenPay (HTTP Basic Auth con la llave privada) vía `httpx`. El endpoint/payload de `payouts` sigue la documentación pública de OpenPay; no hay credenciales de sandbox en este entorno para verificarlo en vivo — **validar contra el sandbox real antes de aprobar el primer pedido en producción**. Credenciales en `Settings` (`OPENPAY_ID`, `OPENPAY_PRIVATE_KEY`, `OPENPAY_PRODUCTION`), sin configurar por defecto: la función falla con error claro en vez de intentar pagar. Un pedido y su pago **siempre** nacen de una acción manual del admin (ver Compras arriba) — no existe ningún camino automático que dispare un pago por sí solo.
- Ventas: `ventas`+`detalle_ventas`. `venta_service.crear(db, usuario, items, forma_pago)` recibe el objeto `Usuario` completo (para leer `usuario.sucursal_id`), exige caja abierta, bloquea si la caja ya excede el límite de efectivo (ver `caja_service.excede_limite` arriba), evita oversell contra el stock de la sucursal del cajero, congela `precio_unitario`, genera movimientos de salida en Inventario para esa sucursal, y recibe `forma_pago` (`efectivo` | `tarjeta` | `transferencia`, default `efectivo`). Solo un método por ticket — no hay desglose de pago mixto en un mismo ticket (YAGNI: el cliente no confirmó necesitarlo, se agregaría una tabla `venta_pagos` si aparece esa necesidad). `caja_service` solo suma al efectivo físico las ventas con `forma_pago=efectivo`; tarjeta/transferencia se reportan aparte en `CajaResumenOut` pero no afectan `monto_esperado`. Sigue sin haber integración bancaria real — la terminal de tarjeta es un dispositivo físico aparte. Sin cambio de modelo en Multisucursal: la venta ya sabe su sucursal transitivamente vía el cajero que la registra.
  - `Venta.estado` (`EstadoVenta`: `completada` | `cancelada`, default `completada`): una venta cancelada (ver Cancelación abajo) queda excluida de todo agregado — `venta_repository._filtrar(..., excluir_canceladas=True)`, usado por `resumen`/`mas-vendidos`/`por-dia`/`por-sucursal`, nunca por `GET /ventas` (el historial sí la muestra, con su badge de estado en frontend). Enum de Postgres `estado_venta` — SQLAlchemy con `Enum(PythonEnumClass)` guarda el *nombre* del miembro (`COMPLETADA`/`CANCELADA`), no `.value`, mismo criterio que `forma_pago`.
  - `Venta.caja` (relationship `lazy="joined"` a `CajaSesion`) + `Venta.sucursal_nombre` (property, `self.caja.sucursal_nombre`): resuelve la sucursal de una venta vía `caja_id → CajaSesion → Equipo → sucursal_id`, mismo camino que ya usaba `reporte_repository.ventas_por_sucursal_del_dia` — ahora expuesto también en `VentaOut` para listados/filtros cross-sucursal. `Venta.usuario` (relationship `lazy="joined"`) + `Venta.usuario_nombre` (property): igual, para el cajero que la registró — `VentaOut.usuario_nombre` alimenta la columna Cajero del hub de Ventas.
  - `GET /ventas` admite `sucursal_id` (join `Venta→CajaSesion→Equipo`, filtra por `Equipo.sucursal_id`, cross-sucursal si se omite — a diferencia de Productos/Inventario/Compras, no pasa por `resolve_sucursal_id`, mismo criterio que Reportes) y `usuario_id` (filtro directo por cajero, sin join). Todos los endpoints de `/ventas` que agregan datos (`resumen`, `mas-vendidos`, `por-dia`, `por-sucursal`) comparten el mismo set de filtros vía `venta_repository._filtrar(stmt, desde, hasta, forma_pago, sucursal_id, usuario_id, excluir_canceladas)` — un solo lugar que arma los `WHERE`/`JOIN`, cada endpoint solo cambia el `SELECT`.
  - `GET /ventas/resumen` (`VentaResumenOut`, sin paginar): `venta_repository.resumen` corre **tres** queries independientes (no un solo join) — sumar `Venta.total` contra un join con `DetalleVenta` multiplicaría cada total una vez por línea de esa venta; `total_articulos` sale de una segunda query que sí necesita ese join (`SUM(DetalleVenta.cantidad)`); `utilidad_total`/`articulos_con_costo` salen de una tercera, filtrada a `DetalleVenta.costo_unitario IS NOT NULL` — nunca cuenta una línea sin costo como utilidad 0. `margen_pct` (`venta_service.resumen`) = `utilidad_total / (suma de subtotales con costo conocido) × 100`, `None` si ninguna línea del rango tiene costo. `venta_service.resumen` devuelve un `NamedTuple` (`ResumenVentas`) en vez de una tupla posicional — el router arma `VentaResumenOut(**resumen._asdict())` directo, los nombres de campo coinciden 1:1 con el schema. Además del bruto (`total_monto`) trae `total_neto` (= `total_monto` − `devoluciones_monto` del propio período, ver Devoluciones abajo — el KPI "Ventas" que ve el admin) y los totales de `devoluciones_monto`/`devoluciones_cantidad`/`cancelaciones_monto`/`cancelaciones_cantidad` del rango (fecha de la propia devolución/cancelación, no de la venta original).
  - `GET /ventas/mas-vendidos` (`list[ProductoVentaOut]`, `limite` default 5): `venta_repository.ranking_productos` agrupa `DetalleVenta` por producto (mismos filtros), ordenado por cantidad desc; `venta_service.mas_vendidos` corta los primeros `limite`. Solo cuenta productos con ≥1 venta en el rango — no es la misma señal que `stock_bajo`/`sin_stock` de `reporte_service` (esas miden inventario, esto mide frecuencia de venta). Sin endpoint simétrico de "menos vendidos": el complemento accionable de este ranking es "Atención" en el frontend, que reusa las alertas de `reporte_service` en vez de una métrica pasiva (ver `docs/FRONTEND.md`).
  - `GET /ventas/por-dia` (`list[VentaPorDiaOut] {fecha, total_monto, cantidad}`): agrupado por `func.date(Venta.created_at)` (huso horario de negocio, ver Zona horaria de negocio abajo) — alimenta el gráfico de tendencia del hub.
  - `GET /ventas/por-sucursal` (`list[VentaPorSucursalOut] {sucursal_id, sucursal_nombre, total_monto, utilidad_total, cantidad}`, sin `sucursal_id` como parámetro — es lo que se agrupa): `venta_repository.por_sucursal` agrupa por `Equipo.sucursal_id`, ordenado por venta desc, solo sucursales con ≥1 venta en el rango. Alimenta el ranking de sucursales del hub, visible únicamente con "Todas las sucursales" seleccionada.
  - `GET /ventas/reporte-productos` (`list[ProductoReporteOut]`, sin `limite`): base de la exportación "Productos vendidos" — a diferencia de `/mas-vendidos` (top-N para la card en pantalla), trae **todos** los productos con ≥1 venta en el rango, con `sku`/`categoria_nombre`/`utilidad_total`/`margen_pct` por producto. `venta_repository.reporte_productos` corre dos queries agrupadas por producto (no una con `case()`): una para cantidad/monto sobre todas las líneas, otra para utilidad solo sobre líneas con `costo_unitario` conocido — mismo criterio de `resumen()` (una línea sin costo no debe contar utilidad 0, subestimaría el margen), fusionadas en Python por `producto_id`. `margen_pct` es `None` por producto cuando ninguna línea de ese producto en el rango tiene costo cargado.
  - `GET /ventas/devoluciones-cancelaciones` (`list[MovimientoReversaOut] {tipo, id, venta_id, created_at, sucursal_nombre, actor_nombre, motivo, monto_total}`): base de la exportación homónima — el detalle fila por fila, distinto de `/resumen` (que solo trae el agregado monto+cantidad). `venta_service.devoluciones_y_cancelaciones` llama `devolucion_repository.listar_periodo`/`cancelacion_repository.listar_periodo` (mismo bucketing por fecha de la propia acción, no de la venta original, que `resumen()` de cada repo) y mezcla las dos listas en Python ordenadas por fecha desc — dos tablas distintas, pocas filas por período típico, no vale un `UNION` SQL para esto.
- Devoluciones (`app/models/devolucion.py`, `devolucion_service`): reversa total o parcial de una venta ya cobrada — el cliente regresa producto físico, la venta original sigue siendo válida (solo se netea en reportes). **La `Venta`/`DetalleVenta` original nunca se edita** — es registro histórico inmutable; `Devolucion`(`venta_id`, `actor_id`, `motivo`, `monto_total`, `movimiento_caja_id` nullable) + `DetalleDevolucion`(`detalle_venta_id`, `cantidad`, `subtotal`) son un movimiento aparte que la referencia. `POST /ventas/{venta_id}/devoluciones` (`DevolucionCreate {items: [{detalle_venta_id, cantidad}], motivo}`) + `GET /ventas/{venta_id}/devoluciones` (historial, usado por `VentaDetalleDialog`/`DevolucionDialog` en frontend). Rechaza una venta `cancelada` (`VentaCanceladaError`, 400) — no hay nada que devolver de un ticket que nunca debió contar.
  - Ventana: **24 horas** desde `Venta.created_at` (`devolucion_service.VENTANA_DEVOLUCION_HORAS`), comparado en UTC (ventana relativa, no boundary de día calendario — mismo criterio que "últimas 48h" de `faltante_caja`, ver Zona horaria de negocio arriba). Pasado ese plazo, `FueraDePlazoError` (400).
  - Permiso: `Usuario.puede_hacer_devoluciones` (booleano, mismo patrón que `puede_retirar_excedente` — admin lo asigna por cajero vía `PATCH /usuarios/{id}/permisos`, que acepta los dos flags de forma independiente, cada uno opcional). Admin siempre puede, sin flag y sin restringir a "su propia venta que armó" — el ticket ya es la prueba de compra, cualquier cajero autorizado puede procesar el folio que sea. Mismo permiso habilita `POST /ventas/{id}/cancelacion` (ver Cancelación abajo) — reversar dinero/inventario es la misma clase de acción sea cual sea la razón.
  - Cantidad: `devolucion_repository.get_cantidad_devuelta(detalle_venta_id)` suma lo ya devuelto en devoluciones previas de esa línea — no se puede devolver dos veces la misma unidad (parcial hoy, el resto después, sigue validado contra lo real disponible).
  - Inventario: siempre reingresa a la **sucursal de la venta original** (`venta.caja.equipo.sucursal_id`), no a la del actor — el producto físicamente vuelve donde se vendió, sin importar quién procese la devolución.
  - Efectivo: solo si `forma_pago == efectivo`. Sale de la caja que el **actor tiene abierta en este momento** (`caja_repository.get_abierta_for_update_by_usuario`), nunca de la caja original de la venta (puede ya estar cerrada — es un corte final e inmutable, reabrirla para ajustarlo rompería esa garantía). Un cajero sin caja abierta no puede procesar una devolución en efectivo (`CajaNoAbiertaError`, de dónde saldría físicamente el dinero). Un admin sin caja abierta sí puede — la devolución se registra igual (inventario ya revertido), solo sin `MovimientoCaja` (`movimiento_caja_id` queda `null`), mismo criterio que el retiro de excedente remoto: el admin no maneja el efectivo físico de una sucursal en la que no está parado. Genera un `MovimientoCaja` real (tipo salida, motivo `"Devolución venta #{id}"`) en el momento — no se difiere al `motivo_diferencia` del corte de caja, que es la señal de "faltante *sin explicar*"; mezclar ahí devoluciones normales (ya explicadas y ya reflejadas en `monto_esperado` al instante) le quitaría valor a esa alerta. Tarjeta/transferencia nunca tocan caja, igual que en la venta original.
  - Auditoría: `venta_devuelta` sobre la entidad `venta`, con `devolucion_id`/`monto_total`/`motivo` en el detalle.
- Cancelación (`app/models/cancelacion.py`, `venta_service.cancelar`): anula la venta **completa** — error del cajero que nunca debió cerrarse (producto/precio equivocado, forma de pago errónea, operación duplicada), a diferencia de una devolución (cliente regresa producto de una venta válida). `Cancelacion`(`venta_id` único, `actor_id`, `motivo`, `monto_total`, `movimiento_caja_id` nullable, `created_at`) — mismo shape que `Devolucion` pero sin tabla de detalle propia, siempre es el ticket entero. `POST /ventas/{venta_id}/cancelacion` (`CancelacionCreate {motivo}`) + `GET /ventas/{venta_id}/cancelacion` (`CancelacionOut | None`).
  - Mismo motor de reversa que una devolución total (inventario a la sucursal original, efectivo de la caja abierta del actor, mismos criterios de ventana de 24h y permiso — ver Devoluciones arriba), pero además marca `Venta.estado = cancelada`: la venta deja de contar en `resumen`/`mas-vendidos`/`por-dia`/`por-sucursal` desde la raíz, no solo se netea.
  - Mutuamente excluyente con devolución: rechaza si la venta ya tiene alguna `Devolucion` (`TieneDevolucionesError`, 400) o ya está `cancelada` (`VentaYaCanceladaError`, 400) — no tiene sentido cancelar un ticket ya parcialmente devuelto, ni cancelar dos veces.
  - Auditoría: `venta_cancelada` sobre la entidad `venta`, con `cancelacion_id`/`monto_total`/`motivo` en el detalle.
- Reportes (`app/modules/reportes/router.py` + `app/services/reporte_service.py`, todo admin-only, ninguno usa `resolve_sucursal_id` — a diferencia de Productos/Inventario/Compras, estos endpoints son deliberadamente cross-sucursal, pensados para vistas de un vistazo sobre todo el negocio, ver `docs/FRONTEND.md`):
  - `cajas_abiertas` (`GET /reportes/cajas-abiertas`) devuelve `list[CajaResumenOut]`, una entrada por cada caja abierta ahora mismo — con N cajas simultáneas no existe "la caja actual" singular, y por lo tanto tampoco fallback a la última cerrada. Sin consumidor en el frontend hoy — Ventas es la única pantalla de entrada del admin (ver `docs/FRONTEND.md`) y no necesita esta vista — pero se mantiene porque la señal ("qué cajas están abiertas ahora, en cualquier sucursal") sigue siendo válida y es la base natural de una vista de ese tipo si hace falta más adelante.
  - `GET /api/reportes/resumen-sucursales` (`reporte_service.resumen_sucursales`): una fila por sucursal activa con `ventas_hoy`/`cantidad_ventas_hoy` (**todas** las ventas de hoy en esa sucursal, sin importar si la caja que las originó ya cerró — join `Venta`→`CajaSesion`→`Equipo`→`sucursal_id`, `reporte_repository.ventas_por_sucursal_del_dia`) + `efectivo_esperado`/`cajas_abiertas`/`cajas_excedidas` (solo cajas **actualmente abiertas**, agrupadas en Python vía `caja_service.resumenes(get_abiertas())` — `CajaSesion` no tiene `sucursal_id` propio, se resuelve con un mapa `equipo_id → sucursal_id` armado desde `equipo_repository.get_activos` para evitar N+1) + `equipos_activos` (capacidad configurada, para el "N de M cajas abiertas" del dashboard).
  - `GET /api/reportes/atencion` (`reporte_service.atencion` → `AlertaOut`, heterogéneo a propósito: cada `tipo` es una alerta de negocio distinta con su texto ya compuesto en el backend): agrega 5 fuentes —
    1. `caja_excedida`: cajas abiertas con `monto_esperado` por encima del límite de su sucursal (`limite_efectivo_para_sucursal`), una alerta por caja (menciona si el cajero `puede_retirar_excedente`).
    2. `caja_sin_cierre`: cajas abiertas hace más de `HORAS_CAJA_SIN_CIERRE` (24h).
    3. `stock_bajo`: `reporte_repository.productos_bajo_umbral` (solo si `umbral_stock_bajo_default` está configurado) — `join` contra `StockSucursal`, cualquier producto con stock en o debajo del umbral entra. Solo detecta stock bajo donde ya existe una fila de `StockSucursal` — una sucursal sin ningún movimiento de inventario todavía (ver `sin_stock` abajo) no genera esta alerta aunque el umbral esté configurado.
    4. `sin_stock`: corre **siempre** (no depende de `umbral_stock_bajo_default`). `reporte_repository.total_productos_activos` (conteo simple) y `conteo_con_stock_por_sucursal` (`StockSucursal.cantidad > 0`, agrupado por sucursal, un solo `join` — sin cross join) le dan a `reporte_service._alertas_sin_stock` lo necesario para restar "productos activos" menos "con stock positivo" por cada sucursal activa (`sucursal_repository.get_activas`); el resultado ya cubre tanto una fila explícita en 0 como la ausencia total de fila (sucursal que hereda el catálogo global pero nunca recibió una entrada de inventario), sin necesitar generar el producto cartesiano Producto×Sucursal.
    5. `faltante_caja`: `auditoria_repository.get_recientes_por_accion(db, "caja_cerrada", desde=hace 48h)`, filtra en Python `detalle["diferencia"] < 0` — `Auditoria.detalle` es `JSON` genérico (no `JSONB`), sin operador de containment eficiente para filtrar en SQL, y el volumen de cierres de caja no lo justifica. Excluye los eventos ya acusados (ver `AlertaAcuse` más abajo).
  - Acuse de alerta (`app/models/alerta_acuse.py`, `AlertaAcuse`): "ya lo revisé" — solo para alertas basadas en un hecho histórico inmutable, hoy únicamente `faltante_caja` (`reporte_service.TIPOS_ACUSABLES`). Las demás (`caja_excedida`/`caja_sin_cierre`/`stock_bajo`/`sin_stock`) describen una condición viva que se resuelve sola en cuanto se arregla el problema real — acusarlas a mano solo escondería algo que sigue vivo, así que no está permitido (`acusar_alerta` rechaza cualquier `tipo` fuera de esa lista con `TipoAlertaNoAcusableError`, 400). `tipo`+`referencia_id` (`UniqueConstraint`) identifica la alerta puntual — para `faltante_caja`, `referencia_id` es el `id` del propio evento de `Auditoria` — genérico a propósito por si otro tipo de alerta puntual lo necesita después, sin rediseñar la tabla. `alerta_acuse_repository.crear` es idempotente (un doble clic o dos admins a la vez no truena, el `IntegrityError` del `UniqueConstraint` se traga en un `SAVEPOINT`). `POST /api/reportes/atencion/acuse` (admin-only, `{tipo, referencia_id}`).
  - `sucursal_repository.get_activas`/`equipo_repository.get_activos`/`auditoria_repository.get_recientes_por_accion` son utilidades chicas que solo consumen estos reportes.
  - `AlertaOut.sucursal_id`/`equipo_id`/`auditoria_id`: identifican la fila exacta detrás de cada alerta puntual (`caja_excedida`/`caja_sin_cierre` llevan sucursal+equipo; `faltante_caja` lleva el id del propio evento de auditoría) — el frontend arma con esto un link directo a esa fila y la resalta, en vez de mandar solo a la página general. `stock_bajo`/`sin_stock` llevan siempre su propio `sucursal_id` — una alerta por sucursal afectada, nunca una mezclando varias (ver `_alertas_stock_bajo`/`_alertas_sin_stock` arriba): el link de "Ver productos" del frontend solo puede aterrizar en una sucursal a la vez, así que es la única forma de que el admin sepa cuál sucursal tiene el problema y a cuál ir.
- Rango de fechas (`auditoria_repository`, `movimiento_inventario_repository`): el filtro `hasta` compara `created_at < hasta + 1 día` (no `<= hasta` a medianoche) — el día seleccionado queda incluido completo, incluyendo lo ocurrido hoy.
- Zona horaria de negocio (`app/core/tiempo.py`, `hoy_negocio()`): todo default de "fecha actual" que delimita un **día calendario** (`reporte_service.resumen_sucursales`) usa `hoy_negocio()`, que fija `ZoneInfo("America/Mexico_City")` explícito — coincide con el `TimeZone` de la sesión de Postgres (configurado a nivel de base/rol, no por la app), que es lo que `func.date()` sobre una columna timestamptz ya usa en SQL para convertir a hora local (mismo criterio en `venta_repository.por_dia`, sin necesitar `hoy_negocio()` porque ahí el rango lo define el filtro `desde`/`hasta`, no un default de "hoy"). Deliberadamente **no** depende de dónde esté físicamente el admin que hace la request ni del reloj del servidor donde corra la app: "hoy" siempre significa "hoy en las sucursales", nunca "hoy donde está el admin" ni "hoy en UTC". Los `datetime.now(UTC)` que miden **duración/ventana relativa** en vez de un día calendario (antigüedad de una caja abierta, "últimas 48h" de faltantes de caja) sí usan UTC — ahí no hay boundary de día que alinear con ninguna zona.
- Superuser / plan (`RolUsuario.SUPERUSER`, `app/modules/superadmin/`): tercer rol, dueño de Soluciones Web (nosotros) — no un rol de negocio del cliente. Modelo de despliegue es **single-tenant por cliente** (cada instalación = su propio backend+DB, decisión explícita frente a multi-tenant real: sin tabla `Empresa`, sin `tenant_id` en ninguna tabla, cada deploy es autocontenido). El superuser no tiene acceso a ningún módulo de negocio (`require_role` en cada router existente sigue siendo un allowlist explícito de `ADMIN`/`CAJERO` — agregar `SUPERUSER` al enum no le abrió ninguna puerta que no se le diera a propósito). Su único endpoint es `GET`/`PUT /api/superadmin/plan` (`plan_service`, admin-only reemplazado por `require_role(RolUsuario.SUPERUSER)`).
  - `ConfiguracionNegocio.limite_equipos` (nullable, mismo patrón fila-única que `limite_efectivo_caja`): cupo de **hardware físico** vendido a esta instalación (impresora + lector + terminal + caja registradora = un `Equipo`) — el negocio real detrás: "muy difícilmente quien contrata el software ya tiene el equipo, se ofrece como kit completo". Nulo = sin límite (default de instalaciones existentes/dev, hasta que el superuser configure un cupo real para ese cliente). Deliberadamente **no** es un enum de planes nombrados ("Individual"/"Multicaja") — sería una capa de nombres sin nada real detrás; el número de equipos habilitados ya es la única variable de negocio que importa, y el superuser lo ajusta directo cuando el cliente compra un kit nuevo.
  - `equipo_service._validar_cupo`: compara `equipo_repository.contar_activos` (todos los equipos activos de la instalación, cross-sucursal — el cupo es de la instalación completa, no por sucursal) contra `limite_equipos`. Se revisa tanto en `crear` (alta de equipo nuevo) como en `cambiar_estado` cuando pasa de inactivo a activo — sin este segundo chequeo, desactivar y reactivar un equipo existente esquivaría el tope. `LimiteEquiposAlcanzadoError` → 400 con el número de cupo en el mensaje (`equipos/router.py`); el admin nunca ve ni edita `limite_equipos` directamente (no viaja en `ConfiguracionNegocioOut`/`Update`, ni en `/configuracion` — ese endpoint sigue siendo `require_role(ADMIN)` puro), solo el aviso de bloqueo cuando lo alcanza.
  - Alta del usuario superuser: `scripts/seed_superuser.py` (mismo patrón que `seed_admin.py`), condicionado a `SUPERUSER_EMAIL`/`SUPERUSER_PASSWORD` en `.env` — sin configurar, el script no crea nada (no todo deploy necesita este acceso; instalaciones ya entregadas a un cliente no deberían tener un superuser activo salvo que Soluciones Web lo esté operando).
- Multisucursal: `Sucursal`+`Equipo` (Fase 1) — catálogo (`Producto`/`Categoria`/`Subcategoria`/`Proveedor`) sigue global; stock, caja y compras son por sucursal.
  - `Sucursal` (`app/models/sucursal.py`): `nombre`, `direccion`/`responsable`/`telefono` (todos opcionales, identifican dónde está y a quién llamar), `limite_efectivo_caja` (opcional, override propio — ver `caja_service.limite_efectivo_para_sucursal` arriba), `activo`.
  - `GET /api/sucursales/{id}/cajas` (`caja_service.estado_cajas_por_sucursal`, admin-only): una fila por cada `Equipo` configurado en la sucursal — abierto o no, a diferencia de `GET /reportes/cajas-abiertas` que solo ve las abiertas. Por equipo: `estado` (`abierta`/`excedida`/`cerrada`), cajero en turno (`cajero_usuario_id`/`cajero_nombre`) si está abierta, `monto_esperado`, `limite_efectivo` ya resuelto, `fecha_apertura` o `ultimo_cierre` según corresponda (`caja_repository.get_ultima_cerrada_by_equipo`). Es el dato que alimenta el hub "Sucursales y cajas" del frontend (ver `docs/FRONTEND.md`) — desde ahí el admin retira excedente o cierra la caja de un cajero por contexto de caja (sucursal+equipo), usando los mismos `POST /usuarios/{id}/caja/...` de siempre.
  - `Usuario.sucursal_id` nullable (admin no pertenece a ninguna, ve todas remotamente) pero obligatorio para `cajero` vía `CHECK ck_usuarios_cajero_requiere_sucursal` a nivel de base de datos, no solo validación de app. `Equipo` (caja registradora física, un nombre deliberadamente distinto de "Terminal" — esa palabra ya la usa el negocio para la terminal de tarjeta BBVA) pertenece a una `Sucursal`.
  - `caja_repository`: `get_abierta_by_usuario`/`get_abierta_for_update_by_usuario`/`get_ultima_cerrada_by_usuario` resuelven la pregunta del día a día ("cuál es MI caja"), más `get_abierta_by_equipo` (pre-check al abrir) y `get_abiertas()` (el conjunto completo, sin filtro).
  - `caja_service.abrir(db, usuario_id, equipo_id, monto_inicial)`: valida que el equipo exista/esté activo y pertenezca a la sucursal del usuario (validación **server-side** — el filtrado del dropdown en frontend es solo UX), pre-checks de "ya tengo caja abierta" y "ese equipo ya está ocupado" (`CajaYaAbiertaError`/`EquipoOcupadoError`), catch genérico de `IntegrityError` como respaldo de carrera entre el pre-check y el insert.
  - `resolve_sucursal_id` (`app/api/deps.py`): dependency compartida por Productos/Inventario/Compras — para `cajero` devuelve siempre `usuario.sucursal_id` (ignora cualquier valor recibido); para `admin` (que no pertenece a ninguna) exige el query param `sucursal_id`, 400 si falta. Evita repetir esta lógica en cada router.
  - Fase 2 (stock por sucursal): `StockSucursal` (PK compuesta `producto_id`+`sucursal_id`, tabla de hechos pura — ausencia de fila = stock cero, se crea perezosamente en el primer movimiento vía `stock_sucursal_repository.get_or_create_for_update`). `ProductoOut` (catálogo puro, usado en referencias anidadas de compras/movimientos) no tiene el campo `stock`; `ProductoStockOut` lo agrega solo para el listado/detalle de `/productos`, construido a mano en `producto_service` (no hay `from_attributes` posible: el ORM `Producto` no tiene ese atributo).
